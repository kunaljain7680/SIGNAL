# 1. CORE GOAL

Build **SIGNAL**, a serious, top-tier portfolio project for a ~1-YOE developer targeting strong:

- SDE-1
- Backend Engineer
- AI Engineer
- AI Platform Engineer
- Backend / Platform Engineer

The goal is not merely to make a beautiful dashboard.

The goal is to build a **real, deployed, technically deep product** whose engineering can be defended in interviews.

## What Signal is

> **Signal is a personalized technology-intelligence platform for developers.**

Core problem:

> There is too much technology information and too little time. A developer cannot continuously research technologies, trends, job demand, open-source activity, and ecosystem changes and decide what actually deserves attention.

Core promise:

> **SIGNAL — Focus on what matters. Leave the noise.**

Signal continuously monitors the technology ecosystem, evaluates evidence, compares that evidence with the user's skills/career goals, and recommends:

- **LEARN**
- **WATCH**
- **LATER**
- **HYPE RISK / IGNORE**

The product is **not primarily a news feed**.

GitHub/HN/jobs/community information is **evidence**.

The product is the **personalized relevance decision**.

The key questions Signal should answer are:

> **What changed?**  
> **What matters?**  
> **Why does it matter to me?**  
> **What should I do?**

# 18. WHY PG_TRGM?

`pg_trgm` is PostgreSQL's fuzzy text matching capability.

Useful for:
- aliases
- typos
- near-matches

Example:

```text

   ↓

```

It should be tried before using an LLM when deterministic matching is sufficient.

# 31. RELIABILITY MENTAL MODEL

Main pipeline:

```text
Collect
 ↓
Clean
 ↓
Understand
 ↓
Measure
 ↓
Recommend
```

Reliability mechanisms protect this pipeline because systems fail.

## Jobs

> Work that needs to happen.

Example:

```text
"Process today's GitHub data"
→ job
```

## Job State

> Where that work currently is.

Example:

```text
PENDING
PROCESSING
DONE
FAILED
```

## Async Processing

> Slow work runs in the background instead of blocking an HTTP request.

```text
API request
 ↓
create job
 ↓
worker processes
 ↓
save result
```

## Worker

> A background process that picks up and executes jobs.

## Checkpointing

> Remember how far expensive work got.

```text
FETCH ✅
RESOLVE ✅
REASONING ✅
PUBLISH ❌

restart
→ PUBLISH
```

## Idempotency

> Processing the same event/job more than once should not create an incorrect duplicate result.

## Retry

> Try a failed operation again when the failure may be temporary.

## Exponential Backoff

> Wait longer between retries.

```text
30 sec
 ↓
2 min
 ↓
8 min
```

## DLQ

> A safe place to park work that repeatedly fails so it can be recovered later.

```text
retry
retry
retry
 ↓
DLQ
 ↓
recovery
```

Important:

> Every source can independently retry/DLQ.

Example:

```text
HN      ✅
GitHub  ❌ → retry → retry → DLQ
Jobs    ✅
```

GitHub failing does not stop HN or Jobs.

This is **fault isolation**.

## Backpressure

> Don't accept/process more work than the system can safely handle.

## Rate Limiting

> Restrict how often we call an external API.

## Cursor / Incremental Fetching

> Remember where previous ingestion stopped so we fetch only new data.

## ETag / Conditional Request

> Ask whether something changed before downloading it again.

## Cron / Scheduler

> Starts work at a scheduled time.

# 33. WHY WE DON'T USE KAFKA / REDIS / KUBERNETES

We are not saying these technologies are bad.

We are saying they are **not justified by Signal's current workload**.

## Kafka would become useful for things such as:
- multiple independent consumers of the same stream
- high-throughput event streaming
- large-scale event replay

Current:

> PostgreSQL is enough.

## Redis would become useful for:
- extremely hot reads
- high-throughput distributed rate limiting
- fast ephemeral coordination

Current:

> PostgreSQL + materialized current state is enough.

## Kubernetes would become useful for:
- many independently scalable services
- substantial orchestration requirements

Current:

> one deployable backend is enough.

Core principle:

> **Do not add infrastructure because it looks impressive.**

# 34. FAILURE MAP

| Failure | What Signal does |
|---|---|
| HN fails | Retry → eventually DLQ |
| GitHub fails | HN and Jobs continue independently; GitHub retries/DLQs |
| Worker crashes | Resume from state/checkpoint |
| Duplicate event | Idempotency prevents duplicate |
| LLM fails | Deterministic score still works |
| LLM returns bad JSON | Validate → retry/fallback |
| DB transaction fails | Transaction rolls back |
| Source becomes stale | Confidence drops / stale state is shown |

# 40. BUILD PHILOSOPHY

Signal should be built feature-by-feature with AI assistance.

Workflow:

> **Understand → Design → AI-assisted implementation → Run → Break → Test → Explain → Move on**

The user should NOT simply tell AI:

> "Build Signal."

Instead, implement one bounded feature at a time.

For each feature:

1. Understand the concept.
2. Understand why Signal needs it.
3. Ask AI to implement only that feature.
4. Run it.
5. Break it deliberately.
6. Test correctness/recovery.
7. Explain the implementation.
8. Only then move on.

Goal:

> **AI accelerates implementation, but the user understands and can defend the system.**
